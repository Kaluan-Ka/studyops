# Google Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir leitura pública do StudyOps e exigir login Google para qualquer ação que grave progresso, evidência ou nota, garantindo a criação de `profiles` e o funcionamento de `auth.uid()`.

**Architecture:** Um `AuthProvider` client-side usará o browser client existente, manterá a sessão em um contexto global e sincronizará o profile do usuário. Um `AuthControl` fixo no shell oferece login/logout sem impedir a navegação pública. Componentes que gravam dados (`MissionProgressPanel` e `StudyNote`) consultarão o mesmo contexto e bloquearão ações sem sessão; o Supabase continuará sendo a autoridade final por meio das policies RLS. Uma migration privada criará `profiles` automaticamente após cada novo `auth.users`, enquanto o cliente fará reparo idempotente para usuários antigos.

**Tech Stack:** Next.js App Router 16, React 19, TypeScript, `@supabase/ssr`, `@supabase/supabase-js`, Supabase Auth Google OAuth, PostgreSQL RLS, Node test runner.

## Global Constraints

- Conteúdo de home, fundamentos, etapas, missões e sessões permanece público.
- Login será somente por Google nesta fatia.
- Iniciar uma missão só será persistido após autenticação; navegar para uma missão continua público.
- Progresso, evidência, notas e qualquer nova mutação de usuário exigem sessão autenticada.
- A criação de `profiles` terá trigger pós-signup e reparo idempotente no cliente.
- Não usar `service_role`, secret key ou `user_metadata` para autorização.
- Não relaxar grants, policies RLS ou a FK composta de `mission_evidence`.
- Notas continuam em `localStorage` para usuários autenticados; não criar tabela de notas agora.
- Não alterar a estrutura de `mission_progress` ou `mission_evidence`.
- Não implementar dashboard real, ciclos semanais, projetos de portfólio, arquivos, email/senha ou magic link.
- Preservar as alterações existentes em `package.json`, `supabase/config.toml` e `scripts/supabase-local.sh`.
- Antes de qualquer comando contra Supabase, confirmar que o alvo é o banco local; não executar `--linked`, `--project-ref`, `db push` ou escrita remota.

```ts
export type ProfileUpsert = {
  id: string;
  display_name: string | null;
};

type ProfileUser = {
  id: string;
  email?: string | null;
  user_metadata?: Record<string, unknown> | null;
};

export function buildProfileUpsert(user: ProfileUser): ProfileUpsert {
  const metadata = user.user_metadata ?? {};
  const displayName = firstNonBlank(metadata.full_name, metadata.name, user.email);

  return { id: user.id, display_name: displayName };
}

function firstNonBlank(...values: unknown[]): string | null {
  for (const value of values) {
    if (typeof value !== "string") continue;
    const trimmed = value.trim();
    if (trimmed) return trimmed;
  }
  return null;
}
```

- [ ] **Step 3: Escrever o trigger**

Substitua o arquivo vazio gerado por:

```sql
create or replace function private.handle_new_auth_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  insert into public.profiles (id, display_name)
  values (
    new.id,
    nullif(
      btrim(
        coalesce(
          new.raw_user_meta_data ->> 'full_name',
          new.raw_user_meta_data ->> 'name',
          new.email
        )
      ),
      ''
    )
  )
  on conflict (id) do nothing;

  return new;
end;
$$;

revoke all on function private.handle_new_auth_user() from public;
revoke all on function private.handle_new_auth_user() from anon;
revoke all on function private.handle_new_auth_user() from authenticated;

drop trigger if exists on_auth_user_created on auth.users;

create trigger on_auth_user_created
  after insert on auth.users
  for each row
  execute function private.handle_new_auth_user();
```
